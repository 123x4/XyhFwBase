# 上板 HEX 核对（用户提供的 Sample.hex）

文件：128,692 字节，`sha256 dc2bda5a…`。只读核对，未改任何文件。工具：自写 Intel HEX 解析 + Capstone（Thumb）反汇编。

## 1. 容器与布局

- Intel HEX 校验和全部正确，2,859 条数据记录。
- 有效载荷 **45,720 字节**；区域分布：
  - `0x2FC`：CRP 字 `0xFFFFFFFF`（未加密，startup.s 的标准写法）
  - `0x3F00`：`AA AA 00 00`，Bootloader 的应用标记
  - `0x4000–0xEFFF`：应用区，填满 45,056 字节
  - `0xF000–0xF28F`：656 字节，`MCU_inside_Flash` 常量块
- 向量表：`MSP = 0x10001E48`，Reset = `0x9F69`（Thumb `0x9F68+1`），HardFault = `0x9F6F`，符合 scatter（app 起始 `0x4000`）。
- ROM 占用 45,720 / 49,152 字节（48 KiB 应用区），**余量 3,432 字节（7.0%）**。
- 与仓库里 11-20 的旧 `output/Sample.hex` 相比有 35,576 字节不同，确认是重新构建的产物，不是旧文件。

## 2. 确认是我们约定的那版源码

- 字符串区有 `PASS`、`FAIL`、指向 `Hall_H6_Diagnostic` 的指针，以及
  `"[I]%s: H6_CAL %s n=%u w0=0x%04X w1=0x%04X\r\n"` → H6 诊断固件。
- 反汇编（应用区 `0xB49A` 起，函数被 -O2 内联）逐条对上了落地代码：
  - `muls r0, 48` → `us × 48`，且乘完**没有加/减**，说明 `H6_PULSE_TRIM_COUNTS` 确实是 0；
  - 与 `65500` 比较并夹紧，`uxth` 后作为 `counts`；
  - `TCR/CTCR/TC/PC/PR/MCR` 依次清零（含 `CTCR=0`）；
  - 进入前先取 `IOCON->PIO1_15` 快照，再 `& ~7` 切 GPIO；
  - `MRS primask`（`0xB4EA`）+ `CPSID i`（`0xB4EE`），高电平期间屏蔽；
  - `TCR=1` → `SET[1]` 置 bit15 → 读 `TC` 作起点 → `ldr/uxth/sub/cmp/blo` 轮询；
  - `CLR[1]` 拉低 → `TCR=0` → 恢复 PRIMASK；
  - `bl 0x4E00`（`CT16B1_DelayUs`）做低等待；
  - 最后用快照恢复 `PIO1_15`（SCK1）。

结论：**这就是计数式脉冲 + trim=0 的那一版**，没有残留 `DrvGPIOOutput(1,15,1)` 的 H5 时序路径。

# H6 计数式脉冲补丁落地复核

对象：Codex 应用 [H6-pulse-counts.patch](H6-pulse-counts.patch) 后的 `app/button.c`（11:28），以及 11:29 刷新的 Windows 测试包。本轮只核对，未改代码。

## 1. 结论

符合预期。Codex 保留了“计数式 + 单 trim 常量 + 仅高电平屏蔽”的结构，另外做了 4 处改进，逐条看都是正向的：

| 改动 | 评价 |
| --- | --- |
| 进入时快照 `sckFunction = LPC_IOCON->PIO1_15`，退出整寄存器恢复 | 比原来的 `reg &= ~7; reg \|= 3` 更稳：连上下拉/驱动位一起还原，不会把别处改过的位覆盖成固定值 |
| 切 GPIO 前先 `LPC_GPIO->CLR[1] = sckMask` | 先把输出锁存器清零，再切 FUNC=0，避免锁存器残留高电平造成上升沿毛刺；此刻 SCK1 空闲为低，切换无跳变 |
| 先开 CT16B1 时钟，再写 TCR/CTCR/TC/PC/PR/MCR；补了 `CTCR = 0` | 顺序更正确；CTCR 显式置定时器模式，不依赖复位默认值 |
| 先按 int32 夹紧，再转 `uint16_t counts` | 比较两端同为无符号，语义更清楚，也避开有/无符号比较告警 |

其余与草案一致：`H6_PULSE_TRIM_COUNTS = 0`、低等待仍走 `CT16B1_DelayUs()`、诊断传 `128U/60U`、H5 分支一字未动。

- **包与工作区同步**：ZIP 内 `EM_HapticMouse/app/button.c` 与工作区 `sha256` 完全一致（`3139f7d1…`），`Sample.uvproj` 的 `<Define>` 为空，`my_board.h` 只启用 `GT_LINA_T1A_H6_PWM`，`H6_SCK_HIGH_TRIM_ONE_CYCLE` 已无引用。
- **H5 分支不变**：用 `cpp` 分别展开改动前快照与当前文件，`-DGT_LINA_T1A_H5` 下忽略空行后完全一致。

- **边界**：`counts` 上限 65500 拍 = 1364.58 µs；td10/td6/td1（6144/1872/240 拍）都在内。

## 3. 对 Codex 评审里两个疑问的回应

**“旧 DelayUs 在短参数处有特殊分支，不能断定短命令无解”。**
特例只影响 `us <= 2`（直接返回或只启动立刻停表）。td1 落在 3–5 区间，`DelayUs` 的等待是 `us - 2` 个整数微秒，步进仍是 1 µs：传 4 等 2 µs、传 3 等 1 µs。叠加实测约 3.26 µs 开销，得到 5.26 / 4.26，仍分别高于/低于 4.75–5.25。所以“整数微秒无法命中 td1 窗口”的结论不变，与特例无关。

**“固定修正量能否同时满足三个窗口”。**
trim 是固定绝对偏置（拍数），与脉宽无关，理论上对 128/39/5 µs 同时成立。但要承认一个差别：td1 只有 240 拍，轮询退出的量化（约 3–5 拍 ≈ 0.06–0.10 µs）相对占比更大。因此 td1 验收建议抓 100 条以上看分布，不只看均值；只要极差 ≤0.2 µs、均值落在 5.00 ±0.1，就说明同一个 trim 够用。

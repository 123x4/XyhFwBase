# DeepSeek H6 计数式脉冲补丁评审与落地

已通过 `patch -p1 --dry-run` 并实际应用 DeepSeek 补丁。H6 仍使用 `Hall_CLK_Command_SET()` 入口，高电平改用 CT16B1 以 48 MHz 计数，低等待复用 `CT16B1_DelayUs()`。校频传入 128 µs 和 60 µs，`H6_PULSE_TRIM_COUNTS=0`。本次同时调整了外设初始化顺序，先打开 CT16B1 时钟，再设置定时器模式和寄存器，并在切换到 GPIO 前把 SCK 输出锁存器清零。计数的有符号修正先夹紧，再转成 `uint16_t` 与无符号已走拍数比较。 [原始补丁](../DeepSeek_Analysis/H6-pulse-counts.patch) · [落地代码](../app/button.c#L807)

## 评审结论

- 保留高电平附近的 PRIMASK 短临界区，下降沿后恢复进入时状态。只屏蔽 USB 和系统 tick 仍可能留下其他可屏蔽中断拉长高脉冲。5 µs 的命令只有 ±0.25 µs 裕量。若以后以 1 kHz 使用 td1，单就 5 µs 高电平的比例约 0.5%，该比例未包含临界区的少量开销。
- CT16B1 在高脉冲后停表，当前 60 µs 低等待立即通过 `DelayUs` 重设 PR=47。现有触觉和 Hall 延时调用在主流程中共用定时器，当前诊断能串行使用。后续若允许在 ISR 中调用相同延时，需要重新检查并发访问。
- 48 MHz 的计数粒度约 20.83 ns，适合验证 td1 的窄窗口。旧 128 µs 波形推不出短命令必然无解，尤其旧 `DelayUs` 在短参数处有特殊分支。可以先用 td10 标定公共修正，但仍要实测 td6 和 td1，确认固定修正是否能同时满足三个窗口。
- 65500 拍的上限约 1364.58 µs，覆盖本次和拟接入的 5、39、128 µs 命令。以后若要发 2 ms 高脉冲，应另行扩展计时范围。

## 上一轮 CSV 复核

第 1、2、7 条从最后一个短时钟下降沿到下一条长高脉冲上升沿分别只有 4.46、4.44、4.36 µs。其余有后续脉冲的事务约等待 20.093–20.098 ms。结合该版只在两个回读通过时等待 20 ms 的逻辑，这支持第 1、2、7 次未通过。记录在第 16 条之后结束，最后一次的两个回读字仍需原始 `H6_CAL` 确认。若同次采集覆盖了完整执行且固件按正常循环退出，预期是 `PASS n=16`。

第 7、10 条低等待分别为 64.94、64.95 µs，比常见值约长 2.3 µs，两条仍满足 >50 µs。SCK 单通道不能确认中断来源。第 10 条之后有 20 ms 等待，反映这类延长没有伴随每次回读失败。若冷启动多次仍有随机失败，先收好原始回读值和波形，再判断 MISO、启动校准或其他原因。

## 验证和下一轮数据

Cortex-M0 Clang 对 H6 脉冲代码启用 `-Wconversion`、`-Wsign-compare` 并通过。H5 PWM、IRPT_V4 和 V4_HALL_HPTIC_V4 的相关预处理输出一致。当前服务器未安装 ARMCC build 960 或 Windows Keil，未生成新的 HEX，也无法直接接入板子和 Saleae。 [已更新的 Windows 测试包](Lina-H6-校频诊断-Windows.zip)

在 Windows 使用包内 `Sample.uvproj` 重建并烧录后，按 CH1 接 SCLK_0、80 MS/s、1–2 秒、80–200 µs 高脉宽触发，先 Start 再冷启动。导出 16 条完整波形与一行对应的 `H6_CAL`。建议三次冷启动分别保存，以比较首条和重复波形。首轮用 trim=0 的均值计算 `round((128.00 - 均值µs) × 48)`，然后重测确认。当前 128.1–128.2 µs 只是估计值。
